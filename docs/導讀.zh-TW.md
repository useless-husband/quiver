# quiver 導讀（給第一次看這個專案的人）

這份文件用白話說明 quiver 在做什麼、為什麼這樣做，讓你在面試時能自己講清楚。
技術細節在 [DESIGN.md](DESIGN.md)，量測數字在 [benchmarks.md](benchmarks.md)。

## 它解決什麼問題

現在的 AI 應用（搜尋、推薦、聊天機器人查資料）會把文字、圖片轉成一串數字，叫做
「向量」（例如 768 個小數）。意思相近的東西，向量也靠得近。於是「找出跟這句話
最像的 10 篇文章」就變成「在一百萬個向量裡找最近的 10 個」。

一個一個算距離（暴力搜尋）一定對，但太慢。向量資料庫要做到：

1. **快**：每秒回答上萬次查詢，只看一小部分資料；
2. **準**：找到的 10 個裡，大部分真的是最近的 10 個（這叫 recall，召回率）；
3. **不掉資料**：程式當掉、被強制關閉，已經回答「寫入成功」的資料都還在；
4. **能加條件**：例如「只找 2020 年以後、英文的文件」。

quiver 是一個從零寫的、小而完整的向量資料庫（Rust），每一項都有測試和量測。
它不是第一個這樣的東西（hnswlib、FAISS、Qdrant 都是成熟的前輩），它的價值是：
程式碼小到看得完、每個宣稱都能自己跑指令驗證、基準測試誠實寫出輸在哪裡。

## 7 個關鍵觀念（附生活比喻）

### 1. HNSW：多層的「人脈網」
**比喻**：你想找一位住在台南、會修古董鐘的師傅。你不會打電話給全台灣的人，而是
先問一個認識很多縣市的朋友（上層），他介紹台南的朋友（中層），再介紹到街坊（最
底層），一步步靠近。HNSW 就是這樣的圖：上層點少、連得遠，底層點多、連得近。
搜尋時從最上層貪心地往目標走，到底層再用一個寬度 `ef` 的「候選名單」仔細找。
`ef` 越大越準、越慢，這就是 recall 和速度的取捨。

### 2. 選鄰居的啟發式規則：不要只交同一圈的朋友
**比喻**：如果你的 16 個朋友全住同一棟樓，你很難認識別棟的人。HNSW 加新節點時，
只有「它離我比離我已選的朋友都近」的候選才會被留下，讓鄰居分散在不同方向，
資料成群（cluster）時圖才不會斷成孤島。

### 3. SIMD 距離計算：一次算 4 個數
**比喻**：收銀員一次刷一件 vs 一次刷一整籃。Apple M 系列晶片的 NEON 指令一次處理
4 個小數；quiver 再開 4 條獨立的累加線，讓 CPU 不用等上一個加法做完。量到的結果：
768 維時比一般迴圈快約 7 倍。int8（整數）版本用 `SDOT` 指令，一次乘加 16 組數字。
執行時才偵測 CPU 支援什麼指令（runtime dispatch），沒有就退回一般版本。

### 4. 量化（壓縮）＋重新排序
**比喻**：先看縮圖挑出 40 張可能的照片，再打開原圖仔細比，留下最好的 10 張。
int8 量化把每個數字從 4 bytes 壓成 1 byte（4 倍小），PQ（乘積量化）把一整段數字
換成「最接近的代表點編號」（16 倍小）。圖的走訪用壓縮版，最後用原始向量重排。

### 5. WAL（預寫日誌）：先記帳，再做事
**比喻**：銀行櫃員先把交易寫進帳本、蓋章，才去動金庫；就算停電，翻帳本就能補回來。
quiver 收到寫入時，先寫進 WAL 檔並用 `F_FULLFSYNC`（macOS 上真正逼硬碟把快取寫進
去的指令）存好，才回答「成功」。多個寫入可以共用一次存檔（group commit，像電梯
一次載很多人），所以不會慢太多。

### 6. LSN（流水號）：吵架時誰先誰後
**比喻**：兩個人同時改同一筆資料，看收據上的流水號，號碼大的算數。每個操作在
WAL 裡都有遞增的 LSN；就算兩個執行緒完成的順序顛倒，記憶體裡的結果還是跟「照
日誌順序重播一次」一模一樣，所以重開機後狀態不會變。

### 7. 段（segment）、檢查點與壓實（compaction）
**比喻**：每天的流水帳寫滿一本就封存（sealed），封存的帳本只讀不改；刪除只在旁邊
貼「作廢」標籤（tombstone）。作廢的太多時，把舊帳本重抄成一本乾淨的新帳本，這就
是 compaction。封存的檔案用 `mmap` 直接對應到記憶體，開檔不用整個讀進來。

### 加碼：過濾搜尋怎麼選策略
**比喻**：要找「台南的古董鐘師傅」，如果台南的人很少，直接把台南的人全部問一遍
（暴力搜尋）最快也最準；如果台南的人很多，才走人脈網、只是跳過非台南的人。
quiver 先精確算出有幾筆符合條件，再用一個公式決定走哪一條路。

| `src/index/graph.rs` | HNSW 本體：插入、搜尋、選鄰居、並行安全、結構檢查 |

| `src/quant/` | int8 量化、PQ、k-means |
| `src/storage/wal.rs` | 預寫日誌、group commit、殘缺尾巴的處理 |
| `src/storage/segment.rs` | 封存段的檔案格式與檢查碼 |
| `src/storage/fs.rs` | `F_FULLFSYNC`、`mmap`、原子性換檔、目錄鎖 |
| `src/payload.rs` | 條件過濾的語法與索引 |
| `src/collection/` | 資料庫核心：寫入流程、LSN、檢查點、壓實、當機復原 |
| `src/server.rs` / `src/client.rs` | HTTP API 與小型 HTTP 用戶端 |
| `src/cli/` | `quiver` 指令、各種基準測試 |
| `tests/crash.rs` | 用 `kill -9` 殺掉伺服器，驗證已回覆成功的資料都還在 |
| `bench/` | 跟 hnswlib、FAISS、NumKong、SimSIMD 比較的腳本與結果 |

## 10 個可能被問的面試題

1. **為什麼不用暴力搜尋？**
   一百萬筆 768 維向量，每次查詢要算一百萬次距離；HNSW 只需要幾千次，代價是可能
   漏掉少數真正的最近鄰（recall 不到 100%）。

2. **recall@10 是什麼？**
   回傳的 10 筆裡，有幾筆屬於「真正最近的 10 筆」，再取平均。真正答案用暴力搜尋算。

3. **M 和 ef 怎麼影響結果？**
   M 是每個點最多連幾個鄰居（越大圖越好走、越佔記憶體）；ef 是搜尋時候選名單的寬度
   （越大越準、越慢）。基準測試就是把 ef 從 10 調到 512，畫出 recall 對速度的曲線。

4. **多個執行緒同時插入，怎麼保證不出錯？**
   每個節點有自己的一把小鎖，只在改它的鄰居清單時鎖；讀的人完全不鎖，用原子操作
   和記憶體順序（Release/Acquire）保證讀到的每個編號都是已經準備好的節點。
   壓力測試還抓到一個真的競爭條件（節點把自己選成鄰居），已修正並加了回歸測試。

5. **怎麼保證「回覆成功」的資料不會掉？**
   先寫 WAL 並強制存到硬碟，再改記憶體，最後才回覆。`tests/crash.rs` 在大量寫入時
   用 `kill -9` 殺掉伺服器，重開後逐筆檢查，四輪都沒有遺失。

6. **為什麼 macOS 要用 F_FULLFSYNC？**
   macOS 的 `fsync` 只把資料交給硬碟，硬碟可能還放在自己的快取裡，停電會掉；
   `F_FULLFSYNC` 要求硬碟把快取也寫進去。

7. **刪除怎麼做？為什麼不直接從圖裡拿掉？**
   先標記（tombstone），搜尋時照樣經過它、但不回傳它，圖才不會斷；作廢太多時用
   compaction 重建一張乾淨的圖。

8. **量化會不會讓結果變差？**
   會一點，所以最後用原始向量重排前 `k × 4` 個候選。int8 在 Fashion-MNIST 上幾乎
   沒有損失；PQ 壓得更小，召回率上限較低，數字在 benchmarks.md。

9. **跟 hnswlib、FAISS 比起來如何？**
   在這台 M5 上：hnswlib 的 ARM 版本沒有 SIMD 距離函式，所以 quiver 比它快；
   用同樣的「一般迴圈」距離比較時，兩者相差不到 3%，表示圖演算法表現接近。FAISS 的
   HNSW 在 Fashion-MNIST 單執行緒時比 quiver 快 12-15%，在 GloVe 上則是 quiver 較快；
   詳細數字與輸掉的地方都寫在 README。

10. **有什麼還沒做好？**
    每個集合只有一個可寫入的段、搜尋是一段一段依序做、compaction 每次都合併全部、
    沒有帳號驗證和複寫（replication）。這些都列在 README 的 Limitations。
